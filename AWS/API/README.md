# API 実行方式

## 結論

Jira などの実装方式に倣い、**期間無制限の PAT（Personal Access Token）を発行し、そのトークンを使って API を実行する**方式が適切。

- 既存の ID トークンは、ブラウザアクセス時に取得する前提があり、CI や自動処理に組み込む際の障壁になりやすいです。
- さらに ID トークンには有効期限があり、長期間の継続利用には不向きです。
- API Gateway の API キーは、ユーザーごとの識別や認証には適していません。
- API キーと PAT の暗号化強度は、両方とも HTTPS を使う前提では同程度です。
- しかし、ログ漏えいのリスクでは **Authorization ヘッダー** の利用の方が安全です。多くのシステムが自動でマスクするためです。
- 一方で `x-api-key` は、アクセスログにそのまれ残るケースがあり、設定を誤るとキーが露出する危険があります。

---

## 1. PAT を採用する理由

PAT を採用する主な理由は、**API 実行時に毎回ブラウザ認証を要求しない**ことです。これにより、CI/CD や自動スクリプト、ローカル検証、バックグラウンドジョブへの組み込みが容易になります。

> ID トークンは「ブラウザログイン用の JWT」であり、有効期限が短いのが特徴です。  
> PAT は「API 実行用のトークン」として、長期間の利用を前提に設計されます。

---

## 2. なぜ Cognito でトークン管理をしないのか

結論から言うと、**人と API トークンの紐づけやメタデータ管理は RDS で管理すべき**です。Amazon Cognito での管理は推奨されません。

Amazon Cognito は、ユーザー認証とログイン状態の管理に特化したサービスです。つまり、Cognito は「人の身元を確認する」ための基盤であり、**「ユーザーごとに複数の API トークンを動的に作成・管理するデータストア」ではありません。**

### 問題点

- **1 人のユーザーが複数のトークンを持つケースに対応しづらい**
  - 開発者は「CI/CD 用」「ローカル検証用」「スクリプト用」など、複数の PAT を使い分けることが一般的です。
  - Cognito のカスタム属性に持たせようとすると、容量制限や配列の扱いの制約にぶつかります。

- **詳細なメタデータ管理が難しい**
  - トークン名
  - 有効期限
  - 有効 / 無効（Revoked）状態
  - 最終利用日時
  - などの管理は、Cognito の属性だけでは検索や更新のしやすさが十分ではありません。

- **RDB で管理したほうが運用上安全かつ柔軟**
  - ユーザー ID とトークンの紐づけを管理しやすく、削除、期限切れ、失効処理、監査ログの記録にも向いています。

---

## 3. 正しい役割分担: Cognito と RDS の共存

ブラウザでログインし、PAT を発行する仕組みを作る場合、Cognito と RDS は以下のように役割を分担します。

### Amazon Cognito の役割

- 「人間の本人確認」を担う
- ユーザーのログイン処理
- ID / パスワードやユーザー情報の管理
- ID トークン（JWT）の発行

### RDS の役割

- 「人と API トークンの紐づけ」を管理する
- ユーザー ID と PAT のハッシュ値を保存する
- トークンのメタデータを管理する
  - トークン名
  - 発行日時
  - 有効期限
  - 状態
  - 最終利用日時

---

## 4. PAT 発行フローの全体像

以下が、推奨する PAT 発行の流れです。

1. **ログイン（Cognito）**
   - ユーザーがブラウザでログインし、Cognito から ID トークン（JWT）を取得します。

2. **トークン発行リクエスト（API Gateway + Lambda）**
   - ユーザーが画面上の「新規 PAT 発行」ボタンを押し、トークン名（例: `GitHub Actions用`）を入力してリクエストを送ります。
   - このときヘッダーに Cognito の ID トークンを含めます。

3. **認証と発行処理（Lambda → RDS）**
   - カスタムオーソライザーなどで ID トークンを検証し、現在のユーザー ID を特定します。
   - Lambda 側でランダムなセキュア文字列を PAT として生成します。
   - PAT は平文で保持せず、**安全のためハッシュ化**して保存します。
   - RDS に以下のようなレコードを保存します。

```text
user_id: user_123
token_hash: $2b$12$...
 token_name: GitHub Actions用
expires_at: 2027-03-01
status: active
```

4. **画面への返却**
   - 生成された平文の PAT をブラウザに一度だけ返します。
   - DB にはハッシュだけを保存するため、ブラウザで一度だけ見せる瞬間を逃すと、二度と平文のトークンを確認できません。
   - これは Jira や GitHub と同じ設計です。

---

## 5. ID トークンと PAT の比較

| 区分 | ID トークン | PAT |
| --- | --- | --- |
| 主な用途 | ブラウザログイン認証 | API 実行認証 |
| 取得方法 | Cognito から発行 | ブラウザから PAT 発行 API で発行 |
| 有効期限 | 短い（通常は数分〜数時間、長くても 1 日程度） | 長期利用を前提とできる |
| 利用場所 | ブラウザのセッション | CI/CD、ローカル、スクリプト、バックグラウンド処理 |
| 認証頻度 | 都度認証が必要 | 反復利用可能 |
| 管理方法 | Cognito | RDS でユーザーとの紐づけとメタデータ管理 |

---

## 6. 最終判断

### 採用案

**PAT を採用する**

### 理由

- API 利用時に都度ブラウザ認証を要求しないため、CI/CD や自動処理に組み込みやすい
- Jira API と同様の運用が可能
- ユーザーとトークンの紐づけを RDS で管理することで、発行、失効、監査、期限管理が可能になる

### まとめ

- **Cognito**: 人の認証とログイン管理
- **RDS**: 人と API トークンの紐づけとメタデータ管理
- **PAT**: API 実行用の長期間利用トークン

この設計により、ブラウザログインと API 利用を両立しながら、運用性と安全性を確保できます。
