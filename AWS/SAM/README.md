# SAMの選定理由
### 1. なぜ「サーバーレス主体構成」にSAMが向いているのか？

#### ① サーバーレス特有のリソースを「直感的」に記述できる

通常のCloudFormationやTerraformでは、API GatewayとLambdaを連携させるために「APIの定義」「メソッドの定義」「統合（Integration）の設定」「Lambda側の実行権限（`AWS::Lambda::Permission`）」など、煩雑なボイラープレート（定型文）を大量に書く必要があります。
SAMはサーバーレスに特化しているため、`Transform: AWS::Serverless-2016-10-31` を宣言し、Lambdaのプロパティに `Events` を数行書くだけで、これらを**裏側で自動的に一括構築・配線**してくれます。

#### ② サーバーレスのライフサイクルに最適化されたビルド・デプロイ

* **`sam build`**: TypeScriptやPythonなどの依存関係（`node_modules` や pipパッケージ）を自動でパッケージングしやすい形にビルドしてくれます。
* **`sam local`**: ローカルのDocker環境を使って、API Gateway ＋ Lambda の挙動をそのままエミュレート実行・デバッグできます。サーバーレス特有の「デプロイしないと動作確認できない」というストレスを大幅に軽減できます。

---

### 2. コスト面でのメリット・特徴

* **SAM自体の利用料は「無料」**
* SAMはあくまで開発・デプロイを補助するツール（CloudFormationの拡張）であるため、SAMを使うこと自体に追加コストは一切かかりません。


* **完全な従量課金によるコスト最適化**
* LambdaもAPI Gatewayも、**「リクエストが処理された時間・回数」にしか費用が発生しない完全な従量課金制**です。
* 開発環境や、アクセスが少ない社内ツール、夜間に使われないAPIなどであれば、維持費（サーバー代）が「0円」になります。


* **複数API構成時のコスト管理のしやすさ**
* SAMテンプレート内で関数ごとにリソースが明確に分かれるため、どのエンドポイント（Lambda）にどれだけのメモリやタイムアウトを設定しているかが一目でわかり、コストの無駄（オーバースペックなメモリ割り当てなど）を最適化しやすくなります。



---

### 3. セキュリティ面のメリット・注意点

#### 【メリット】

* **最小権限の原則（Least Privilege）を自動化しやすい**
* SAMでは、Lambda関数ごとに個別のIAMロールを暗黙的（Implicit）または明示的に簡単に割り当てることができます。「このAPIのLambdaには、特定のDynamoDBテーブルへの読み書き権限だけを与える」といった制御を関数単位でクリーンに分離できます。


* **セキュリティ設定のテンプレート化・コードレビュー**
* API Gatewayの認可設定（CognitoオーソライザーやIAM認証、Lambdaオーソライザーなど）をコードとしてGit管理できるため、意図しない公開設定を防ぎ、チームでのセキュリティレビューが容易になります。



#### 【注意すべきポイント】

* **暗黙的なIAMロールの生成に注意する**
* SAMは非常に便利で、設定を省略するとLambdaに必要な最小限のIAMロールを自動生成してくれますが、複雑なポリシー（別サービスの別リソースへのアクセスなど）が絡む場合は、自動生成に頼らず明示的に `Policies` プロパティやカスタムIAMロールを定義する必要があります。


* **APIのエンドポイント露出管理**
* デフォルトのAPI Gateway作成ではパブリックなエンドポイントになるため、社内向けや特定クライアント向けのAPIであれば、リソースポリシーによるアクセス元IPの制限や、WAF（AWS WAF）の連携をSAMテンプレート側で適宜追加・設定する意識が必要です。

### 4. 実際に動かす最小デモ

`AWS/SAM/demo` 配下に、Lambda + API Gateway の最小構成を作成しました。

#### 1) デモプロジェクトを確認する

```bash
cd AWS/SAM/demo
ls -R
```

#### 2) テンプレートの検証

```bash
sam validate
```

#### 3) ビルド

```bash
sam build
```

#### 4) ローカル関数を実行

```bash
sam local invoke HelloApiFunction --event events/event.json
```

#### 5) ローカルAPIを起動してブラウザ / curl で確認

Docker が入っている環境で実行します。

```bash
sam local start-api
```

別ターミナルで:

```bash
curl "http://127.0.0.1:3000/hello?name=SAM"
```

#### 6) AWSへデプロイ

```bash
sam deploy --guided
```

このデモでは、`/hello` に対して `GET` を受け、`name` クエリを使って応答を返すだけの最小構成です。実際にSAMでAPI GatewayとLambdaが自動で繋がる様子を、数ファイルで体験できます。

### 5. 既存のAPI Gateway + Lambda を SAM 化する一般的な流れ

コンソールで手動作成した既存の構成からSAMテンプレートを起こす場合、大まかに以下の手順で行います。

1. **APIのOpenAPI定義をエクスポートする**
   * API Gateway のコンソールから「OpenAPI 3.0（API Gateway拡張付き）」を選択してYAMLファイルをダウンロードします。
2. **Lambdaのコードをダウンロードする**
   * Lambda のコンソールからコードのZIPをダウンロードします。
3. **SAMテンプレート（`template.yaml`）を新規作成し、組み込む**
   * 新規に `sam init` などでベースのテンプレートを作り、そこにエクスポートしたOpenAPI定義を組み込む（`AWS::Serverless::Api` や `AWS::Serverless::HttpApi` の `DefinitionBody` もしくは `DefinitionUri` に指定する）か、手動で `Events` 定義を書き起こします。

完全なワンクリックでのSAMエクスポート機能はAWSコンソールには備わっていないため、APIのルーティング定義（OpenAPI）をエクスポートし、それをベースにSAMテンプレートを記述・整理していくのが一般的なアプローチとなります。

この流れは、既存のAPI GatewayとLambdaを「コードとして再構成し、Git管理可能な形に変換する」ための実務上の標準的な進め方です。
