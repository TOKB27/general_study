# AWSサービスコスト試算と最適化メモ

## 1. 目的

- AWSサービスの課金メカニズム（何にお金がかかるのか）を理解する。
- システムの成長（初期〜中規模）に伴い、**どのような選択肢がコストにインパクトを与えるのか**を把握する。

---

## 2. サービスごとの課金体系とコストを左右する選択肢

### ① フロントエンド・認証レイヤー

| サービス | 主な課金要素 | コストを左右する選択肢・要因 |
| --- | --- | --- |
| **CloudFront** | アウトバウンドデータ転送量、HTTP/HTTPSリクエスト数 | **Price Class**: 全リージョン利用（Class All）か、日本・北米に限定する（Class 200/100）かで単価が変わる。**キャッシュヒット率**が高いと、S3やオリジンへのアクセス量と転送量を大きく削減できる。 |
| **S3** | ストレージ容量（GB/月）、リクエスト数（GET/PUT など） | **ストレージクラス**: 標準で十分なケースが多く、ログ保存などは Lifecycle により IA や Glacier に自動移行させる。静的ファイル自体が数百 MB 程度で、コストインパクトは小さい。 |
| **Cognito** | MAU（月間アクティブユーザー数） | **無料枠**: 月間 50,000 MAU まで無料。**Advanced Security Features** の有効化で MAU 単価が上がるため、要件に応じた判断が必要。 |
| **Lambda@Edge** | リクエスト数、実行時間（ミリ秒単位） | **実行場所・頻度**: HTML リクエストごとに検証を走らせるか、CloudFront の Viewer Request / Origin Request のどちらで動かすかで差が出る。**メモリ割り当てと処理軽量化**が重要。 |

---

### ② API・ビジネスロジックレイヤー

| サービス | 主な課金要素 | コストを左右する選択肢・要因 |
| --- | --- | --- |
| **API Gateway** | リクエスト数（HTTP API / REST API） | **API タイプ選択**が重要。HTTP API は 100 万リクエストあたり約 $1.00〜、REST API は 約 $3.50〜＋機能拡張があるため、コスト差は約 3 倍以上になることがある。**レスポンスキャッシュ**有効化は Lambda 起動数と DB 負荷の抑制に効く。 |
| **AWS Lambda** | リクエスト数、実行時間 × 割り当てメモリ量（GB-秒） | **アーキテクチャ選択**: x86 から Graviton2 (arm64) に変更すると約 20% のコスト削減が見込める。**メモリ設定の最適化**と**RDS 接続管理**が重要。 |

---

### ③ データベース・運用管理レイヤー

| サービス | 主な課金要素 | コストを左右する選択肢・要因 |
| --- | --- | --- |
| **RDS for PostgreSQL** | インスタンス稼働時間、ストレージ容量（GB/月）、バックアップストレージ容量 | **インスタンスタイプとプロセッサ**: db.t4g などの T 系 ARM インスタンスは db.t3 より低価格で高性能。**Multi-AZ** は可用性向上の代償として料金が倍増しやすい。**Reserved Instances** を長期利用で購入すると 30%〜50% 割引が可能。 |
| **Secrets Manager** | シークレット保持数、API リクエスト数 | **キャッシュ処理の有無**が重要。Lambda のグローバルスコープでシークレットをキャッシュし、リクエストごとに Secrets Manager へ API 呼び出ししないようにする。 |
| **EC2 (Bastion)** | インスタンス稼働時間、EBS ストレージ容量 | **起動スケジューリング**で不要な時間は停止し、**SSM Session Manager** を活用してパブリック IP や EIP を廃止すると固定費を削減できる。 |

## 3. 初期〜中規模システムにおける段階別コスト変動モデル

初期フェーズから規模が拡大した際、**どこが固定費でどこが変動費（従量課金）として効いてくるか**を比較すると次の通りです。

```text
【初期フェーズ：〜1,000 MAU / 低トラフィック】
  ほぼ「RDS インスタンス代＋固定費」が占める（サーバーレス部分は無料枠内〜数ドル程度）
  └ RDS (db.t4g.micro Single-AZ): 約 $15〜20/月
  └ EC2 Bastion (t4g.nano 随時停止): 約 $1〜3/月
  └ Lambda / API GW / CloudFront / Cognito: ほぼ $0 〜 $5
  -------------------------------------------------------------
  概算合計: 約 $20 〜 $30 /月

【中規模フェーズ：〜50,000 MAU / 月間100万〜500万APIリクエスト】
  サーバーレスの従量課金が増加し、RDS も本番運用に合わせたスペックアップが必要になる
  └ RDS (db.t4g.small Multi-AZ + 100GB Storage): 約 $70 〜 $100/月
  └ API Gateway (HTTP API 500万req): 約 $5/月
  └ AWS Lambda (500万実行 / arm64): 約 $5 〜 $10/月
  └ CloudFront + Lambda@Edge: 約 $5/月
  └ Cognito (50,000 MAU以内): $0（無料枠内）
  -------------------------------------------------------------
  概算合計: 約 $85 〜 $120 /月
```

## 4. 実践：AWS Pricing Calculator を使ったコスト見積もり手法

AWS 公式のウェブ見積もりツール **[AWS Pricing Calculator](https://calculator.aws/)** を使って、チームで試算する手順です。

1. **見積もり（Estimate）の作成開始**  
   https://calculator.aws/ にアクセスし、「見積もりの作成（Create estimate）」を選択。対象リージョン（例: `Asia Pacific (Tokyo)`）を指定する。

2. **各サービスの追加とパラメータ入力**  
   検索窓からサービス名を検索し、構成要素を追加していく。

   - **Amazon RDS for PostgreSQL**  
     - Node Type: `db.t4g.micro` または `db.t4g.small`
     - Deployment Option: `Single-AZ` または `Multi-AZ`
     - Storage: General Purpose SSD (`gp3`), 20 GB〜100 GB

   - **Amazon API Gateway**  
     - Type: `HTTP API`
     - Requests: 月間リクエスト数（例: 1,000,000）

   - **AWS Lambda**  
     - Architecture: `Arm64 (Graviton2)`
     - Request Count: 月間実行数
     - Memory: `128 MB` 〜 `512 MB`、平均処理時間（例: 200 ms）

   - **Amazon Cognito**  
     - MAU 数（例: 5,000）を入力し、**50,000 以下なら $0 と計算される**ことを確認する

3. **サマリーの確認と共有**  
   全サービスの試算を追加した後、「見積もりのサマリー」で月額・年額の合計コストを確認する。必要に応じて「共有（Share）」リンクを発行し、ADR や設計資料に添付して共有する。

## 5. コスト最適化のための設計ベストプラクティス（まとめ）

1. **マネージド DB（RDS）のサイズ最適化が最優先**
   - 初期段階では最小スペック（`db.t4g.micro` / `gp3`）から始め、CPU・メモリ・IOPS を監視しながら段階的にスケールアップする。
   - 本番環境でスペックが固まったら **Reserved Instances（1年/3年）** を検討する。

2. **サーバーレス部分は Graviton と HTTP API を徹底選択**
   - Lambda のアーキテクチャを `arm64` に統一する。
   - 特別な要件がない限り、API Gateway は REST API ではなく **HTTP API** を選択する。

3. **無駄な API 呼び出し・通信をアプリケーション実装で防ぐ**
   - Lambda 内で取得した Secrets Manager の認証情報はグローバル変数にキャッシュし、リクエストごとの API 呼び出しを抑える。
   - Biome などでビルドしたフロントエンド成果物の Cache-Control を最適化し、CloudFront でのキャッシュ率を高める。
