## 署名付きURLが安全である理由（仕組み）

1. **改ざん防止（HMAC / デジタル署名）**
* URLパラメータ内に「有効期限」「アクセス対象リソース」「暗号化された署名（Signature）」が含まれています。
* 攻撃者がURLのパラメータ（例: 有効期限を延ばす、別オブジェクトのパスに書き換える）を少しでも変更すると、AWS側の署名検証で失敗し、即座に拒否されます。


2. **一時的なアクセス許可（時限式）**
* 指定した時間（例: 5分間）を過ぎると自動的に無効化されます。

## 発生しうるセキュリティリスクと対策

### 1. URL漏洩による不正アクセス（共有・転載リスク）

* **リスク:** URLを発行された本人がSNSや掲示板に貼り付けたり、第三者に共有した場合、有効期限内であれば**そのURLを知った全員がダウンロードできてしまう**点です。
* **対策:**
* **有効期限（Expiration）を極力短く設定する:** ダウンロード用途であれば **「1分〜5分程度」** など必要最小限に設定します（ダウンロード開始さえできれば、通信途中でURLの有効期限が切れても転送は最後まで完了します）。
* **CloudFront署名付きURLのIP制限を活用する:** 特定のIPアドレス（ユーザーのクライアントIP）からのみアクセスを許可する条件パラメータを署名に組み込むことが可能です。



### 2. 再利用や繰り返しダウンロードによる転送量増大（DoS / 高額請求）

* **リスク:** 有効期限内であれば、同じユーザー（あるいは攻撃者）が短時間に**何百回・何千回もリクエストを送り、S3の転送量コストを高騰させる**リスクがあります。
* **対策:**
* **CloudFrontを挟む:** CDNにキャッシュさせることで、S3への直接アクセスを遮断しコストと負荷を抑えます。
* **WAF（AWS WAF）の導入:** 同一IPからのレート制限（1分あたりのリクエスト数制限）を設けて機械的な大量アクセスをブロックします。



### 3. S3バケット自体の公開設定ミス

* **リスク:** 署名付きURLを導入したつもりで、S3バケット自体のパブリックアクセスを許可してしまう設定ミス。
* **対策:**
* S3の **Block Public Access（パブリックアクセスブロック）** をすべて「有効」にします。
* CloudFront経由の場合は **OAC（Origin Access Control）** を設定し、CloudFrontの特定ディストリビューションからのみアクセスを許可するバケットポリシーを記述します。
